# EDA summary: paysim

> PaySim is itself a simulation. Findings describe the simulator, not real payment fraud.

Generated by `python -m riskstream.cli prepare-data`. All values below are computed; see `eda_report.json` for the full numbers.

## Overview

- Rows: 6,362,620; fraud: 8,213 (0.1291%); about 774 legitimate rows per fraud row.
- Steps 1-743 (743 distinct). One step is one simulated hour, so behavioral windows are defined in hours.
- Missing values: 0 in total.

## Account repetition

- Origin accounts: 6,353,307; 99.85% appear once; max 3 transactions; 0.29% of rows involve a repeat origin account.
- Destination accounts: 2,722,362; 83.12% appear once; max 113 transactions; 64.44% of rows involve a repeat destination account.

## Leakage and simulator artifacts (TRANSFER and CASH_OUT rows)

| signal | legit | fraud |
|---|---:|---:|
| orig_after_zero | 90.10% | 98.05% |
| amount_equals_orig_balance | 0.00% | 97.82% |
| dest_both_zero | 0.06% | 49.63% |
| orig_balance_mismatch | 0.41% | 0.19% |
| dest_balance_mismatch | 22.58% | 56.50% |
| orig_before_zero | 47.37% | 0.50% |

- `is_flagged_fraud` rows: 16. It is the output of the simulator's own rule, so it is excluded from features.
- `orig_balance_after`, `dest_balance_before` and `dest_balance_after` are not available when a transaction is scored (post-event, or another institution's data). They are excluded from model features. `orig_balance_before` is treated as available (the sender's own institution knows it).
